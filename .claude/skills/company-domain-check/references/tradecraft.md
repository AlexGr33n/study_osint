# Tradecraft: граф активів, finding-картки, гігієна доказів, заметність

Дисципліна, перенесена з **elementalsouls/claude-osint** (`skills/osint-methodology`) і переосмислена
в **захисній, discover-only** рамці: знахідки — це те, що власник активу має полагодити, а не кроки
для атаки. Жодних наступальних how-to тут немає навмисно.

## 1. Граф активів

Кожне відкриття — це **типізований вузол**, а не вільний рядок.

Поля вузла: `type`, `key` (типізований dedup-id у форматі `<type>:<value>`), `value`, `sources[]`,
`confidence` (A/B/C/D), `first_seen`, `last_seen`, `attrs{}`.

Типи, доречні для перевірки компанії/домену (лише публічно спостережуване):

| Категорія | Типи |
|---|---|
| DNS / мережа | `domain`, `subdomain`, `ip`, `netblock`, `asn` |
| Сервіс | `certificate`, `mx`, `ns` |
| Юрособа | `legal_entity` (код), `brand`, `email_pattern` |
| Веб | `webapp`, `wayback_endpoint` |
| Фішинг-ризик | `typosquat_domain` |

**Дисципліна:** спершу створи актив, тоді причепи до нього finding. Dedup за ключем — одна сутність
не має розмножуватися в рядках. `sources[]` перелічує **всі** джерела; достовірність спочатку
per-source, потім агрегована. Ребро (зв'язок між вузлами) додається лише коли підтверджене
**правилом трьох** (≥3 незалежні слабкі сигнали АБО 1 сильний + 1 слабкий). Один слабкий сигнал
(спільний favicon-хеш, спільний NS, збіг геолокації IP) — це гіпотеза, а не володіння.

## 2. Finding-картка: дві незалежні осі

Кожна знахідка несе **дві окремі осі**. Їх не можна змішувати.

- **Критичність** — наскільки це небезпечно для угоди/власника: `info` → `low` → `medium` → `high` → `critical`.
- **Достовірність (грейд)** — наскільки ти впевнений, що знахідка реальна: `A` / `B` / `C` / `D`.

Приклад: «DMARC `p=none`» — достовірність A (прямо видно в DNS), але критичність для *угоди* low
(це проблема власника домену, а не ознака шахрайства). І навпаки: «серія позовів про непоставку» може
бути критичністю high, але грейдом C, доки не підтверджено роль компанії у справах.

Формат рядка в memo: `знахідка | критичність | доказ (URL/файл) | грейд`. Сортуй за критичністю,
а не за порядком виявлення. Для exposure-категорій (відкритий `.env`, листящаяся корзина, `DMARC p=none`,
застарілий аплайенс із каталогу KEV) завжди додавай **рекомендацію по усуненню** для власника.

## 3. Грейди та правило трьох

| Грейд | Значення |
|---|---|
| A | офіційний реєстр або ≥2 незалежні надійні джерела |
| B | одне надійне незалежне джерело, прямо спостережене |
| C | висновок із непрямих даних (позначай «висновок/інференс») |
| D | одинична неперевірена згадка; може бути хибною |

**Шляхи апгрейду достовірності (D/C → B → A):** друге незалежне джерело (не передрук першого);
офіційний реєстровий запис; збіг за **ідентифікатором**, а не за назвою. За сумніву — знижуй грейд.
**Правило трьох для атрибуції:** 3 незалежні слабкі сигнали АБО 1 сильний + 1 слабкий. Ніколи не
атрибутуй за одним джерелом, навіть як зачіпку.

## 4. Гігієна доказів і chain of custody

- Для всього, на що зішлешся: **URL + мітка часу в UTC + SHA-256** збереженої копії. `domain_recon.py`
  робить це автоматично (`raw/` + `raw/SHA256SUMS`); для сторінок, відкритих через WebFetch, фіксуй
  принаймні URL і UTC-час перевірки.
- **Артефакт незмінний.** Анотації, спостереження й висновки живуть у memo/нотатці, а не поверх доказу.
  Відредагував те, на що посилаєшся, — зламав ланцюжок походження.
- Розкладай докази **за стадіями** треку (seed → expansion → enrichment), а не за типами файлів:
  цінно, **на якому кроці** зʼявився актив.

## 5. Заметність (detectability) і лестниця відступлення

Познач кожну операцію за слідом, який вона лишає.

| Рівень | Приклади для company/domain DD |
|---|---|
| **Low** | RDAP/WHOIS, DoH, crt.sh / CertSpotter, Wayback CDX, GLEIF, читання реєстрів, WebSearch |
| **Medium** | багаторазовий WebFetch тієї самої сторони-цілі, часті повтори до одного агрегатора |
| **High** | *поза межами skill*: активні скани, перебір піддоменів, валідація кредів, user-enum |

За замовчуванням — **лише Low**. Medium тримай помірним (паузи між зверненнями). High у цьому skill
не роблять узагалі.

**Ознаки, що тебе притримують:** `429` / `Retry-After`; капча; блок-сторінка WAF; `403` тільки з твоєї
IP; раптова зміна відповіді.

**Лестниця відступлення (а не обхід):**
1. Збільш паузу, додай джитер; зменш частоту.
2. Перестань бити в проблемний шлях → візьми інше джерело тієї ж категорії (union).
3. Зроби паузу.
4. Якщо блок WAF / прямий контакт → **зупинись** і познач у «Прогалинах». Обходити захист не можна.

## 6. Стійкість джерел (union, а не один виклик)

Жодне окреме джерело не має «гейтити» цілу категорію. Для кожної категорії став запити до
взаємозамінних бекендів як **об'єднання (union)**: CT-логи (crt.sh, CertSpotter), DoH (Google,
Cloudflare), реєстрація (RDAP, WHOIS), реєстри (офіційний + агрегатори). Мертве джерело — це
подія деградації покриття (лог у `recon.json → errors`), а не «категорія порожня».

## 7. Бюджет часу / профіль роботи

Фіксуй **до** збору, скільки часу й глибини заслуговує питання:
- `quick` (≤15 хв): технічний профіль + ідентифікація за кодом + санкції + скорочене memo.
- `standard` (30–60 хв): повний цикл 0–7.

**Умови аборту:** невідповідність рамок після Кроку 0; домен не зареєстровано / юрособу не знайдено
за кодом → зупинись і повідом; ознаки блокування під час збору (розділ 5).
