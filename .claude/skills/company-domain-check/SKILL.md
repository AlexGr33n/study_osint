# Company & Domain Check → Due Diligence Memo

Мета: дати відповідь на питання **«Чи безпечно мати справу з цією компанією / довіряти цьому
домену, і які саме ризики?»** з доказами, грейдами достовірності та чесно названими прогалинами.
Результат: `dd-<domain>/memo.md` за шаблоном `assets/memo-template.md`.

Методологія навмисно зібрана з двох публічних skill-репозиторіїв і переосмислена в **захисній,
discover-only** рамці (детальна атрибуція — у `homework/README.md` та `homework/reference/`):
- **smixs/osint-skill** — конвеєр по фазах, ескалація «дешеве → дороге», грейди A/B/C/D, правило трьох, рекурсивна самооцінка.
- **elementalsouls/claude-osint** — граф типізованих активів, осі критичність × достовірність (finding-картка),
  гігієна доказів і chain of custody, модель заметності (detectability) + лестниця відступлення, бюджет часу,
  стійкість джерел (union, а не один виклик), трек поверхні атаки «тільки обнаруження».
  **Наступальні частини claude-osint (secret-regex, wordlists, валідатори кредів, user-enum) свідомо НЕ
  використовуються** — вони лежать лише як незмінна довідкова копія в `homework/reference/claude-osint/`.

Вхід: `$ARGUMENTS` — домен, URL, назва компанії або код (ЄДРПОУ / company number / LEI),
опційно країна та режим. Якщо чогось бракує для Кроку 0, спитай користувача одним повідомленням.

| Режим | Час (бюджет) | Кроки | Коли |
|---|---|---|---|
| `quick` | ≤15 хв | 0 → 1 → 2 → 3 (лише санкції) → 6 (скорочене memo) | разова дрібна оплата, підозрілий лист/сайт |
| `standard` (за замовч.) | 30–60 хв | 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7 | новий постачальник, передоплата, партнерство |

Бюджет часу фіксуй **до** збору (принцип з claude-osint): він визначає глибину й момент зупинки, а не навпаки.

## Крок 0 — Межі, мета та правила взаємодії (gate, обов'язково)

1. Запиши **питання** одним реченням і **мету** (напр. «перевірка постачальника перед передоплатою
   200 000 грн»). Без питання не починай збір.
2. **Об'єкт — організація або домен.** Посадові особи (директор, засновники, бенефіціари) перевіряються
   лише *у своїй ролі*: ПІБ, посада, санкції/PEP, судові справи як посадової особи. Не збирай приватне:
   домашні адреси, особисті телефони, родину, особисті соцмережі. Запит фактично про людину → зупинись
   і поясни, що це поза цим skill (це skill `osint`).
3. **Discover-only. Тільки пасивні й публічні джерела.** Заборонено: сканування портів, перебір
   піддоменів/директорій, nuclei/фаззинг, валідація знайдених кредів, user-enumeration, логіни в чужі
   акаунти, обхід CAPTCHA/paywall, куплені бази й витоки, контакт із компанією під легендою.
   Трек поверхні атаки тут закінчується на пасивному спостереженні (`references/attack-surface.md`).
4. Зафіксуй **стартові ідентифікатори** (домен, назва, код, email, IBAN з рахунку) і **критерій зупинки**.

## Крок 1 — Технічний профіль домену (скрипт)

```bash
python "${CLAUDE_SKILL_DIR}/scripts/domain_recon.py" <domain> --company "<юридична назва, якщо відома>" --out dd-<domain>
```

Якщо `python` недоступний, спробуй `python3`/`py`. Скрипт працює лише на stdlib і **не робить жодного
запиту до серверів цілі**: RDAP→WHOIS fallback, DNS через DoH (A/AAAA/NS/MX/TXT, SPF, DMARC),
CT-логи (crt.sh → CertSpotter), Wayback CDX (перший/останній знімок), GLEIF (LEI). Результат:
`recon.md` (зведення), `recon.json` (структуровано), `raw/` + `raw/SHA256SUMS` (provenance).
Триває 1–2 хв: Wayback і crt.sh повільні.

**Заметність (detectability) і лестниця відступлення.** Усі ці джерела — рівня **Low** (пасивні
агрегатори, не сама ціль). Якщо будь-яке джерело віддає `429`/`Retry-After`, капчу чи блок-сторінку:
не повторюй у циклі, а **відступай** — збільш паузу, візьми альтернативне джерело тієї ж категорії,
за потреби зупинись. Обходити захист не можна (деталі — `references/tradecraft.md`).

**Стійкість джерел (union, а не один виклик).** Одне мертве джерело ≠ порожня категорія: crt.sh впав →
бери CertSpotter; Google DoH → Cloudflare DoH; RDAP → WHOIS. Збій фіксуй як подію в `recon.json → errors`
(далі він потрапляє в «Прогалини»), а не як відсутність даних.

Як читати (сигнали скрипта — це **підказки, не висновки**):

| Сигнал | Що означає |
|---|---|
| Домен не зареєстровано (WHOIS: no match) | Адреса з листа/рахунку вигадана або з помилкою. Перевір написання, шукай двійника |
| Вік домену < 90 днів | Типово для фішингу/скаму. Конфлікт із «працюємо з 2012 року» = red flag |
| Перший знімок Wayback раніший за реєстрацію | Домен перереєстровано (drop-catch): стара історія сайту може належати іншому власнику |
| Реєстрант = юрособа | Сильний сигнал зв'язку домен ↔ компанія (часто є в `.ua`, рідко в `.com` через GDPR) |
| Немає MX | Компанія не отримує пошту на свій домен, тож адреса `info@домен` у контактах не працює |
| DMARC відсутній / `p=none` | Від імені домену легко підробити лист. Це знахідка для власника, а **не** доказ шахрайства |
| CT: перелік хостів | Масштаб інфраструктури (api, my, cdn…). Для CertSpotter `first_seen` ≠ вік домену |
| Верифікаційні TXT | Якими SaaS користується організація (Google, Microsoft, Atlassian…). Вказує на реальну операційну діяльність |

## Крок 2 — Ідентифікація юрособи та зв'язок домен ↔ компанія

1. WebFetch сайту: «Про нас», «Контакти», публічна оферта, політика конфіденційності, футер.
   Витягни **повну юридичну назву, код (ЄДРПОУ / company number / VAT), адресу, телефон, email**.
2. Знайди юрособу в реєстрі її юрисдикції (`references/sources.md`). **Ідентифікуй за кодом, не за назвою.**
   Зафіксуй: статус (зареєстровано / в стані припинення / припинено / банкрутство), дату реєстрації,
   адресу, КВЕДи, статутний капітал, керівника, засновників, кінцевих бенефіціарів (КБВ).
3. **Розв'язання тезок.** Назви компаній повторюються («Нова Пошта», «Нова Пошта Глобал», «Нова Пошта
   Інтернешнл» — різні юрособи з різними кодами). Збіг тільки за назвою — гіпотеза, а не ідентифікація.
4. **Зв'язок домен ↔ юрособа підтверджується за правилом трьох** (з обох репо): **≥3 незалежні слабкі
   сигнали АБО 1 сильний + 1 слабкий**. Сигнали: реєстрант у RDAP/WHOIS; код/назва в оферті на сайті;
   домен у реєстрі, LEI-записі, держзакупівлях або офіційних звітах; email на цьому домені в офіційних
   документах. Сам лише футер сайту = **заява компанії** (будь-хто може скопіювати чужий ЄДРПОУ на фейк).
5. Звір дати: реєстрація юрособи ≤ «працюємо з …» на сайті; вік домену правдоподібний для заявленої історії.

## Крок 3 — Санкції, PEP, суди, борги

Перевір **компанію + керівника + засновників + КБВ** (усіх, хто має контроль):

- **Санкції:** OpenSanctions (агрегує ~300 списків, зокрема ООН, ЄС, OFAC, UK), Державний реєстр
  санкцій РНБО, War & Sanctions. Шукай транслітерації (Kyiv/Kiev, ТОВ/LLC/ООО, укр/рос/англ написання).
  Збіг лише за ПІБ/назвою = **гіпотеза D**, підтвердь другим ідентифікатором (код, дата народження,
  громадянство, адреса).
- **Зв'язки з державою-агресором** (засновники/КБВ — резиденти чи громадяни РФ/РБ, спільні власники
  із санкційними особами). Для українського контексту це окремий високий ризик.
- **PEP** серед власників означає посилену перевірку, а не порушення саме по собі.
- **Суди:** ЄДРСР (компанія як відповідач; категорії «стягнення боргу», «шахрайство», «поставка»),
  кримінальні провадження, у яких фігурує компанія.
- **Борги:** виконавчі провадження (АСВП / Єдиний реєстр боржників), податковий борг, анулювання ПДВ.
- **Закупівлі** (для B2B): Prozorro / Clarity Project — історія тендерів, дискваліфікації, скарги.

## Крок 4 — Репутація та adverse media

WebSearch паралельно (українською, англійською, за потреби російською):

- `"<назва>" шахрайство OR скам OR обман OR суд OR "кримінальне провадження"`
- `"<домен>" scam OR fraud OR phishing OR відгуки`
- `"<код ЄДРПОУ>"`: часто знаходить згадки, яких не видно за назвою
- Репутаційні бази доменів: VirusTotal (звіт), Google Safe Browsing (Transparency Report), URLhaus.
  ScamAdviser та агрегатори відгуків — **слабкий сигнал** (оцінка C/D).

Правила: публікація ≠ факт; звинувачення ≠ вирок; фіксуй **дату** й **джерело** кожної згадки.
Відрізняй незалежні медіа від передруків і від PR-матеріалів самої компанії.

## Крок 5 — Верифікація, граф активів та грейди достовірності

1. **Граф активів** (з claude-osint, defensively). Кожен публічно спостережуваний **актив** (домен,
   піддомен, IP, сертифікат, ASN, email-патерн, юрособа) заноси як **типізований вузол** з ключем
   `<тип>:<значення>` і роби dedup за ключем. Ребра — лише підтверджені зв'язки (правило трьох).
   Спершу створюєш актив, тоді чіпляєш до нього finding. «Висячі» нетипізовані рядки графом не є.
2. **Таблиця фактів:** `Твердження | Джерело(а) | Грейд | Перевірено (UTC)`.
   - **A**: офіційний реєстр (ЄДР, Companies House, GLEIF, RDAP реєстру) або ≥2 незалежні надійні джерела.
   - **B**: одне надійне незалежне джерело (якісне медіа, держзакупівлі, офіційний звіт).
   - **C**: висновок із непрямих даних (вік за Wayback, «справжня діяльність» за TXT) з позначкою «висновок».
   - **D**: одинична неперевірена згадка, відгук, анонімний форум, збіг лише за назвою.
3. Заяви компанії про саму себе (сайт, соцмережі, реклама) мають позначку **«заявлено компанією»**,
   доки їх не підтвердить реєстр або незалежне джерело.
4. Якщо джерела **суперечать** — наведи обидві версії з джерелами, не обирай мовчки зручнішу.

Повна дисципліна (граф активів, гігієна доказів, лестниця відступлення, бюджет часу) — `references/tradecraft.md`.

## Крок 6 — Finding-картки, red flags і рівень ризику

Прочитай `references/red-flags.md`. Кожна знахідка оформлюється **finding-карткою** з **двома незалежними
осями** (принцип claude-osint): **критичність** (наскільки це небезпечно для угоди: info / low / medium /
high / critical) і **грейд достовірності** (наскільки ти впевнений у факті: A/B/C/D). Не змішуй їх.

| Рівень | Правило | Рекомендація |
|---|---|---|
| 🟥 Високий | будь-який `critical` на грейді A/B **або** ≥2 `high` | Не продовжувати / ескалювати (юрист, комплаєнс, кіберполіція при фішингу) |
| 🟧 Середній | 1 `high` **або** ≥2 `medium` **або** ключова ідентифікація лише на C/D | Продовжувати з умовами: документи, постоплата, ескроу, договір, повторна перевірка |
| 🟩 Низький | лише `low`/`info`, юрособа та зв'язок домен ↔ компанія на A/B | Продовжувати, стандартний моніторинг |

Ніколи не став 🟩, якщо юрособу не ідентифіковано за кодом. «Недостатньо даних» — валідний висновок
(рівень не нижче 🟧).

## Крок 7 — Memo

Заповни `assets/memo-template.md` і збережи як `dd-<domain>/memo.md` (поруч із `recon.*`).
Мова memo — мова користувача.

- Спершу **BLUF**: рівень ризику, рекомендація, загальна впевненість і 3 головні причини.
- Кожен факт має **джерело (URL) і грейд**. Твердження без джерела видали.
- Обов'язкові розділи **«Суперечності»** і **«Прогалини»**: прогалини теж є результатом перевірки.
- Усі дати й час у **UTC**. Для збережених артефактів вкажи SHA-256 (з `raw/SHA256SUMS`).
- Формулюй коректно щодо реальних компаній: «у реєстрі X зазначено…», «у статті Y стверджується…».

## Самоперевірка перед видачею

- [ ] Питання й мета записані; межі та discover-only (Крок 0) дотримано
- [ ] Юрособу ідентифіковано **за кодом**, тезки відсіяні
- [ ] Зв'язок домен ↔ юрособа проходить правило трьох (або чесно позначено, що ні)
- [ ] Санкції перевірено для компанії **і** для керівника/власників/КБВ
- [ ] Активи типізовано й dedup'нуто за ключем; ребра підтверджені
- [ ] Кожен red flag оформлено finding-карткою: критичність + грейд + доказ (provenance)
- [ ] Є розділи «Суперечності» та «Прогалини»; збої джерел із `recon.json → errors` у них згадано
- [ ] У memo немає приватних даних осіб поза їхньою роллю в компанії

## Антипатерни

1. Вважати сайт компанії доказом її існування. ЄДРПОУ у футері можна скопіювати.
2. Ідентифікувати юрособу за назвою без коду.
3. Видавати DMARC `p=none` або приховані WHOIS-дані за «ознаку шахрайства»: це поширена норма.
4. Вважати збіг імені в санкційному списку підтвердженням без другого ідентифікатора.
5. Ставити 🟩 тільки тому, що нічого поганого не знайшлося. Відсутність доказів ≠ доказ відсутності.
6. Сканувати інфраструктуру цілі «щоб краще побачити», валідувати креди, перебирати піддомени. Це поза discover-only.
7. Продовжувати довбити джерело після `429`/капчі. Потрібна лестниця відступлення, а не обхід.
8. Вважати одне мертве джерело порожньою категорією. Бери альтернативу (union), збій → у «Прогалини».
9. Писати висновки без дат: реєстри змінюються, тож memo без UTC-дати неможливо перевірити.
10. Плутати критичність із достовірністю. Це дві різні осі finding-картки.
