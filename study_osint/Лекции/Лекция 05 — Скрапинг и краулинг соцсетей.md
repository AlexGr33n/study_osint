# Лекция 05 — Скрапинг и краулинг соцсетей

> Оригинальное название: «Соцмережі та медіапростір: збір, моніторинг, базовий аналіз» (файл — *Scraping and Crawling*).
> Практический кейс: собственный «флот» сборщиков Telegram · Discord · WhatsApp · Waydroid.

## О чём лекция

Основы краулинга и скрапинга (термины, типовые проблемы, прокси), затем разбор реальной системы
сборщиков сообщений из мессенджеров: каноническая модель данных, учёт лимитов, ротация аккаунтов,
пределы исторического сбора. Главные уроки: **измеряй причину бана, а не угадывай**, и
**ограничения платформ формируют архитектуру**.

> [!warning] Рамки хранилища
> Часть кейса (self-bot в Discord, регистрация аккаунтов через Android-контейнер, пулы аккаунтов,
> резидентные прокси) — это **серая/наступательная зона**: нарушает ToS платформ и выходит за
> рамки discover-only. Здесь это зафиксировано на уровне концепции и рисков — чтобы распознавать
> и понимать ограничения, а не воспроизводить. Применять — только с авторизацией и законным основанием.

## Краулинг vs скрапинг

| | Краулинг (crawling) | Скрапинг (scraping) |
|---|---|---|
| Вопрос | **ГДЕ** данные? — найти и обойти | **ЧТО** в данных? — извлечь поля |
| Вход | seed-адреса / список целей | HTML, JSON-ответ API, сообщение |
| Выход | список URL, граф ссылок, очередь целей | структурированные записи `author · url · date · text` |
| Пример | Googlebot, Common Crawl, обход каналов | цены, посты, комментарии, профили |

На практике это один конвейер: краулер находит, скрапер достаёт.

### Цикл краулера

```
Seed URLs → Frontier (очередь: приоритет, глубина) → Fetcher (HTTP/API: лимиты, прокси, retry)
   → Parser (HTML/JSON: данные + новые ссылки) → Storage (это уже скрапинг)
   → новые ссылки → Dedup (нормализация URL, seen-set) → новые в Frontier
```

- Цикл крутится, пока очередь не пуста или не достигнут лимит глубины/количества.
- Обход: **BFS** — типично; приоритетная очередь — свежее и важное первым.
- Вежливость: задержки, лимит параллельности, уважение к `robots.txt`.
- В «флоте» frontier — это таблицы `sources.*_targets` с cursor и расписанием (`next_run_at`).

## 4 подхода к извлечению данных

| Подход | Как | Плюсы / минусы |
|---|---|---|
| **HTML-парсинг** | CSS-селекторы / XPath; `requests` + BeautifulSoup / lxml | Быстро, но хрупко к смене вёрстки |
| **Скрытые API** | Сайт сам грузит JSON (XHR/fetch) — смотреть DevTools → Network | Чище и стабильнее HTML |
| **Headless-браузер** | Playwright / Selenium: рендер JS, скролл, клики | Самый медленный и заметный |
| **Официальные API / протокол** | Telegram MTProto (Telethon), Discord REST, WhatsApp Web (OpenWA) | Структурировано, но нужны аккаунты и лимиты |

**Правило:** сначала ищи API (официальный или скрытый); HTML и браузер — когда иначе никак.

## Словарь

- **Seed** — стартовая точка обхода (URL, канал, сервер), задаётся вручную.
- **Frontier** — очередь того, что ещё обойти; порядок выбора = стратегия обхода.
- **Rate limit** — лимит запросов за время на аккаунт/IP; превышение → HTTP 429 / Telegram `FloodWait`.
- **Backoff** — растущая пауза после ошибки (1 → 2 → 4 → 8 с…) + случайный **jitter**; уважать `Retry-After`.
- **Politeness** — добровольные ограничения (напр. 1 запрос / 2 с, ≤2 соединений на домен).
- **robots.txt** — правила для ботов (`Disallow`, `Crawl-delay`); договорённость, а не техническая защита.
- **User-Agent** — как клиент себя называет; дефолтный UA библиотек часто блокируют.
- **Pagination / cursor** — номер страницы «съезжает» при новых записях; cursor — точный маркер «откуда продолжить» (`offset_id` в Telegram, `before=<id>` в Discord).
- **Инкрементный сбор** — каждый прогон берёт только новое после последнего cursor (`min_id=last_id`).
- **Dedup / идемпотентность** — повторный прогон не создаёт дублей: стабильный уникальный ключ, `UNIQUE(source, message_id)` + `INSERT IGNORE`.
- **Proxy / egress** — IP, который видит платформа.
- **Session / token** — сохранённый вход вместо пароля; **утечка токена = полный доступ к аккаунту**.

## Типовые проблемы и что делать

| Проблема | Признаки | Решение |
|---|---|---|
| Rate limits | 429, `Retry-After`, FloodWait, замедление ответов | пейсинг, backoff с jitter, дневной бюджет; **считать запрос ДО попытки** |
| Баны и CAPTCHA | 401/403, челлендж, «подтвердите телефон» | (у автора: ротация, кулдаун проблемного аккаунта, журнал событий) — см. рамки |
| Репутация IP | блок/CAPTCHA с первого запроса с DC-IP | (у автора: резидентные/VPN-прокси) — см. рамки |
| JS-рендеринг | в `requests` данных нет, в HTML только `<div id="root">` | найти XHR в DevTools; headless — крайний вариант |
| Логин и сессии | редирект на вход, внезапные 401 | хранить сессию/токен (не пароль), проверять до прогона, алерт на перелогин |
| Смена вёрстки/API | **тихо** 0 записей / пустые поля без ошибок | контроль «сколько собрано», алерт на ноль, тесты на сохранённых примерах, каноническая модель отдельно от парсера |
| Дубли и пропуски | повторы после рестарта, «дыры» в датах | **сдвигать cursor только после успешной записи**, unique key + `INSERT IGNORE`, проверка непрерывности |
| Право и этика | ToS, авторское право, персданные (GDPR) | собирать минимум, только публичное/доступное легально, ограничить срок хранения, задокументировать цель |

**Три вопроса перед сбором:** нужны ли эти данные для цели? есть ли законное основание? кто получит доступ?

## Прокси (концептуально)

- Прокси скрывает **только IP**. Аккаунт, cookies, User-Agent и поведение выдают так же, как без прокси.
- HTTP(S)-прокси (для HTTPS — туннель CONNECT) vs **SOCKS5** (любой TCP: MTProto, WebSocket).
- Типы: datacenter (низкое доверие, ASN хостинга виден сразу) · residential · ISP (static residential) ·
  mobile 4G/5G (CGNAT) · VPN-выход. Режимы: rotating (новый IP на запрос) vs sticky (1 аккаунт = 1 стабильный IP).
- **Этика резидентных сетей:** это чужие устройства, подключённые через SDK в бесплатных приложениях —
  выбирать провайдеров с прозрачным согласием и KYC.
- **Санкционный риск:** оплата российским провайдерам может нарушать санкции, а провайдер видит ваш трафик.
  Кейс (Qurium, 2025): IP провайдера, связанного с подсанкционной структурой, использованы в DDoS на независимые медиа.
- Ловушка: без `python-socks` Telethon **тихо ходит напрямую** — «утечка IP», похожая на успех.
  Проверять фактический исходящий IP перед прогоном.

> В рамках хранилища прокси нужны только для OPSEC исследователя (не светить свой IP при пассивном
> просмотре), а не для обхода блокировок платформ.

## Архитектура «флота» (кейс)

```
Dashboard (FastAPI): аккаунты · лимиты · здоровье · вебхуки · membership sync
Crawler container: расписание, циклы Telegram + Discord
OpenWA bridge (whatsapp-web.js, headless) → события → вебхук
Waydroid (Android в LXC) → вход в официальный клиент → .session
SOCKS5 egress (VPN-выходы + relay)
            ↓
MySQL: sources.* — конфиг и состояние; results.* — общие таблицы результатов (5,1 млн+ строк)
```

Масштаб: Telegram — 1 452 цели, 6 номеров, 5,1 млн строк; Discord — 5 серверов, ~26 тыс. сообщений;
WhatsApp — 5 целей, пассивно через вебхуки.

### Каноническая модель данных

- **Разделение:** `sources.*` (аккаунты, статусы, кулдауны, бюджеты, цели + cursor + расписание
  `interval/lookback`) и `results.*` (результаты всех сборщиков).
- Общий формат для всех потребителей: **`author · url · date · text`** (+ media, forwards, media_type).
- Каноническая модель живёт отдельно от парсера — смена платформы ломает только адаптер.

## Telegram: главный урок FloodWait

- Пайплайн: пул аккаунтов (round-robin + cooldown) → resolve entity (`username → access_hash`) →
  pull сообщений по per-channel cursor (инкрементно) → общая таблица.
- **Гипотеза** «банят за частоту» была неверной. **Реальность:** бан ~24 ч за **объём** операций
  resolve username (сотни новых resolve = аномалия).
- **Решение:** кэш `access_hash` (≈4,5 тыс. записей) + дневной бюджет resolve на аккаунт (≈60/день) +
  при превышении — **мягко отложить цель** (без ошибки). Итог: 0 банов за объём.
- **Мета-урок:** измеряй причину по логам, не угадывай.

```python
# суть паттерна: кэш дорогой операции + бюджет, учтённый ДО попытки
cached = get_cached_entity(url)
if cached: return peer_from_cache(cached)       # без сетевого запроса
if resolve_count_today(acc) >= BUDGET:
    raise BudgetExceeded                          # → soft-defer цели
bump_resolve_count(acc)                           # считаем ДО: мёртвые цели не сливают бюджет
peer = await client.get_input_entity(url)
store_cached_entity(url, peer)                    # кэш навсегда
```

## Discord и WhatsApp (концептуально)

- **Discord:** сбор через user-token (self-bot) — **прямо против ToS** Discord. Читаются только серверы,
  где аккаунт уже состоит (без auto-join). Ротация по LRU между аккаунтами одного сервера.
- **Классификация ошибок** (полезный общий паттерн): 403 «нет доступа» — не вина аккаунта, не штрафовать;
  401 — токен мёртв → `invalid`; 429/CAPTCHA → кулдаун **только этого** аккаунта, не всего пула;
  все сигналы → журнал `account_events`.
- **Панель риска:** ни одна платформа не говорит «как близко ты к бану» → пишут сигналы-предвестники
  (CAPTCHA, глобальные лимиты, отказы токена, обрывы соединения, ошибки прокси) и сводят в
  зелёный/жёлтый/красный уровень с причинами.
- **WhatsApp (OpenWA-мост):** привязка через QR/pairing-code, пассивный сбор вебхуками, цели — только
  группы/каналы, где номер **уже есть**.
- **Предел backfill (E2E):** каналы не E2E — история до подписки доступна (~100 последних постов);
  группы — **только после вступления** номера: до вступления сообщения этому номеру не доставлялись,
  и ни один клиент их не прочитает.
- Backfill-паттерн: один чат за прогон; 4xx (кроме 409) → пропустить навсегда, 409/5xx → повторить позже;
  идемпотентно (`INSERT IGNORE`).
- **Waydroid** (Android в LXC-контейнере) — для входа/регистрации через официальный клиент с извлечением
  сессии. Фиксируем только как факт: создание/регистрация аккаунтов для сбора — **вне рамок хранилища**.

## Как это строилось (AI-агент)

- Весь флот разработан и обслуживается AI-агентом (Claude Code): читает код, собирает образы, деплоит
  (Portainer, rollback через переименование), сводит статистику.
- `CLAUDE.md`, skills, subagents — «операционная память» команды; MCP подключает БД, очереди, дашборд.
- **Уроки (кэш, ротация, relay) записаны в память агента**, чтобы не наступать на те же грабли.

## Главное для практики

1. Сначала официальный API, затем скрытый JSON-API, и только потом HTML/headless.
2. Инкрементный сбор по cursor; cursor сдвигается **только после успешной записи**.
3. Идемпотентность: стабильный уникальный ключ (`source + message_id`) + `INSERT IGNORE`.
4. Backoff с jitter, уважение `Retry-After`, дневные бюджеты; дорогие операции — кэшировать.
5. Алерт на «0 записей» — парсеры ломаются тихо; тесты на сохранённых ответах.
6. Единая каноническая модель `author · url · date · text` отдельно от адаптеров платформ.
7. Минимизация персданных, законное основание, срок хранения, задокументированная цель; секреты — в `.env`.
8. Собирать «как платформа позволяет»; обход защит и чужие/фейковые аккаунты — вне рамок.

## Домашнее задание

Python-проект, собирающий данные с одной соцсети (Telegram / Discord / WhatsApp) или похожей
(Reddit, Mastodon, публичный Telegram-канал, YouTube-комментарии, RSS-медиа).

- **Обязательно:** инкрементный сбор (cursor / последний id); каноническая модель `author · url · date · text`
  (SQLite / JSONL); пейсинг + backoff на 429; устойчивость и dedup (сбой источника не валит прогон,
  рестарт с курсора); `.env`, README, `requirements.txt`.
- **Сдать:** git-репозиторий + README; пример данных ≥200 записей; отчёт 0,5–1 стр. (источник, лимиты, как справлялись).
- **Оценка:** инкрементность и dedup 25% · лимиты и ошибки 25% · модель данных 20% · код/README/конфиг 20% · отчёт 10%.
- **Бонусы:** ротация ключей/аккаунтов, прокси-выход, дашборд статистики, backfill истории, Docker/compose.
- В рамках хранилища безопасный выбор — RSS, Mastodon API, Reddit API, публичный канал через официальный API.
