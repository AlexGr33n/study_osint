## О чём лекция

Прямое продолжение [[Лекция 11 — Воркшоп по блокчейну и криптоактивам|воркшопа 11]]: там адреса трассировали вручную в обозревателях (peeling-цепочки, пулинг, «хранилища» миксеров, кейс Garantex → A7A5 → Grinex), здесь — **822 942 кошелька** в графовой базе. Цель — превратить интуицию воркшопа в **воспроизводимые запросы, метрики и визуализации**:

- паттерн = запрос, который можно повторить;
- кластер = алгоритм с параметрами, а не «на глаз»;
- тренд = метрика во времени + проверка дрейфа;
- визуализация в Gephi = аргумент в отчёте.

Данные — два научных датасета: BitcoinTemporalGraph (как строят граф и как его размечают методами OSINT) и Elliptic++ (практика). Инструменты: **Neo4j** — хранение, Cypher, алгоритмы GDS; **Gephi** — исследование и визуальная история для отчёта. Сквозное правило: **каждый ответ — гипотеза для офчейн-проверки, а не приговор**.

### Как построен BitcoinTemporalGraph

1. **Сырые данные** — узел Bitcoin Core → файлы `blk*.dat`, первые 700 000 блоков.
2. **Скрипты** — каждый выход (TXO) защищён locking script; нулевые TXO отброшены → более 874 млн скриптов.
3. **Кластеры** — эвристики объединяют скрипты одного владельца → ~252 млн сущностей, это и есть узлы.
4. **Рёбра** — чистая сумма `v(a) = получено − потрачено`: `v > 0` — получатель, `v < 0` — отправитель.
5. **Фильтры** — исключены CoinJoin (JoinMarket, Wasabi, Whirlpool) и colored coins (Omni, Open Assets, EPOBC).
6. **Атрибуты** — у ребра `reveal`, `last_seen`, `total`, min/max/total_sent; у узла степени, суммы, временные границы, размер кластера.

### Формула ребра на примере

Транзакция: входы A = 1,0 BTC и B = 0,5 BTC; выходы C = 1,2 BTC и сдача на A = 0,29 BTC; комиссия майнеру 0,01 BTC.

- `v(a) = Σ выходов a − Σ входов a`: v(A) = 0,29 − 1,0 = −0,71 и v(B) = −0,5 → отправители; v(C) = +1,2 → получатель.
- Доли входов: A = 1,0 / 1,5 = ⅔, B = ⅓.
- Рёбра: A → C = ⅔ × 1,2 = **0,8 BTC**; B → C = ⅓ × 1,2 = **0,4 BTC**. Сдача A → A ребра не создаёт.

Это **модельное решение** (распределение по доле входов): другая модель дала бы другие веса — фиксируем выбор в методологии. Замечание (моё): транзакция не хранит, «чьи» входы оплатили какой выход, поэтому любые веса рёбер в таком графе — оценка, а не наблюдение.

### OSINT-разметка: BitcoinTalk + LLM

Метки узлов получены классическим офчейн-OSINT: контекст с форума даёт атрибуцию ончейн-адресов.

- **Корпус:** BitcoinTalk — 14 067 713 постов, 546 440 тем (англоязычный раздел). Контекст для модели: тема, пост, детали tx + курс USD на дату.
- **Модель:** gpt-4o-mini, 4 типа промптов (депозит, вывод, hot/cold) → рассуждение, название сущности, тип, адреса.
- **Сценарии:**
  - депозит — пользователь жалуется, что средства не зачислены → адрес депозита принадлежит сервису;
  - вывод — сервис сообщил txid → входы tx = горячий кошелёк сервиса;
  - вывод без txid — поиск tx ±3 дня на адрес пользователя с указанной суммой; если она одна — атрибуция.
- **Как метка доходит до узла:** название → одна из 11 категорий (форум, интернет, Wayback Machine); адрес → все скрипты, которые он отпирает → кластер (узел). Несколько разных меток в одном кластере → метку не ставят.

Итог: **34 098 размеченных узлов = 0,014 % графа** (≈ 1 узел из 7 400). Меток мало — сигнал приходится брать из структуры. В шкале грейдов A/B/C/D (навык `osint-research`) такие метки — грейд C (одиночный источник, извлечённый LLM), пока не подтверждены вторым независимым.

## Часть 2. Neo4j: от CSV к паттернам

### Зачем графовая база

Поиск кошельков в пределах 3 шагов от адреса в PostgreSQL — рекурсивный CTE на десяток строк; в Cypher — два:

```cypher
MATCH (:Wallet {address: '1Abc...'})-[:SENT_TO*1..3]->(w:Wallet)
RETURN DISTINCT w.address;
```

PostgreSQL (как в статье) — массовое хранилище на 120 ГБ, выборки, агрегаты. Neo4j — многошаговые пути, паттерны, алгоритмы GDS, быстрая визуальная проверка. **Практическое правило: большое хранилище — в SQL, подграф расследования — в Neo4j.**

### Установка

Версии на ноябрь 2026 (по слайду): Neo4j 2026.10.1 с Cypher 25 по умолчанию; GDS и APOC 2026.10.1 уже лежат в дистрибутиве (`products/` и `labs/`).

- **Neo4j Desktop:** база → Plugins → APOC, Graph Data Science → Install.

### Модель данных

| Элемент | Свойства |
|---|---|
| `(:Transaction)` | `txId`, `timeStep`, `class`, `nIn`, `nOut`, `totalBTC`, `fees`, `outMin`, `outMax` |
| `(:Wallet)` | `address`, `class`, `firstStep`, `lastStep` |
| `[:FLOWS_TO]` | tx → tx (поток средств) |
| `[:INPUT]` / `[:OUTPUT]` | кошелёк → tx / tx → кошелёк (двудольный граф) |
| `[:SENT_TO {n}]` | кошелёк → кошелёк, производное ребро; `n` — сколько раз встретилась пара |

Один датасет — **три графа**: поток средств (tx → tx), взаимодействие кошельков (addr → addr), двудольный (addr → tx → addr).

### Подготовка CSV в pandas (`prep.py`)

- Взять 10 из 184 колонок: 695 МБ → 14 МБ.
- Кошелёк: одна строка + первый и последний шаг (`groupby('address')['Time step'].agg(firstStep='min', lastStep='max')`).
- Self-loops (сдача на тот же адрес) убраны — 45 981.
- Дубли пар → вес `n`: 2 822 983 → 2 775 637 пар, `n` до 87.

Гигиена данных (как в [[Лекция 10 — Автоматизация сбора и гигиена данных]]): каждое преобразование — в скрипте рядом с данными, а не руками в таблице.

### Импорт: LOAD CSV

```cypher
CREATE CONSTRAINT tx_id IF NOT EXISTS
  FOR (t:Transaction) REQUIRE t.txId IS UNIQUE;
CREATE CONSTRAINT wallet_addr IF NOT EXISTS
  FOR (w:Wallet) REQUIRE w.address IS UNIQUE;

LOAD CSV WITH HEADERS FROM 'file:///sent_to.csv' AS row
CALL (row) {
  MATCH (a:Wallet {address: row.input_address})
  MATCH (b:Wallet {address: row.output_address})
  CREATE (a)-[:SENT_TO {n: toInteger(row.n)}]->(b)
} IN TRANSACTIONS OF 20000 ROWS;
```

Ограничения уникальности — **до** импорта, иначе каждый `MATCH` сканирует все узлы. Полный скрипт — `01_import.cypher`. Контрольные числа после импорта: Transaction 203 769 · Wallet 822 942 · FLOWS_TO 234 355 · INPUT 477 117 · OUTPUT 837 124 · SENT_TO 2 775 637. Импорт — 4 мин 17 с на 2 CPU / 7 ГБ RAM, дольше всего SENT_TO (147 с).

### Паттерн → сигнатура → запрос

| Паттерн | Сигнатура в данных | Инструмент | Легитимное объяснение |
|---|---|---|---|
| **Fan-in** (консолидация) | Входящая степень ≫ медианы | `count()` / `gds.degree` REVERSE | Биржа, пул майнеров, донаты |
| **Fan-out** (распыление) | Исходящая степень ≫ медианы, большое `nOut` | `count()` / `nOut` | Пакетные выплаты бирж, зарплаты |
| **Peel chain** | ≥ 5 tx подряд: 2 выхода, малый < 10 % | Путь `*5..8` + `all()` | Обычный кошелёк со сдачей |
| **Цикл** (round-trip) | Путь возвращается к старту за 2–4 шага | `(w)-[*2..4]->(w)` | Переводы между своими кошельками |
| **CoinJoin** | Много входов, равные выходы | Фильтр `nIn`, `nOut`, `outMin ≈ outMax` | Приватность, не преступление |
| **Мост / хаб** | Высокая betweenness между сообществами | `gds.betweenness` + Louvain | Биржа, платёжный шлюз |

**Паттерн — гипотеза:** у каждого есть легитимное объяснение, которое нужно исключить до вывода.

### Cypher-запросы и что они дали на Elliptic++

```cypher
// Fan-in: кто собирает средства
MATCH (s:Wallet)-[:SENT_TO]->(w:Wallet)
WITH w, count(s) AS senders WHERE senders >= 100
RETURN w.address, w.class, senders ORDER BY senders DESC LIMIT 10;

// Экспозиция: куда доходят средства illicit
MATCH (i:Wallet {class: 1})-[:SENT_TO*1..2]->(u:Wallet {class: 3})
WITH u, count(DISTINCT i) AS exposure WHERE exposure >= 5
RETURN u.address, exposure ORDER BY exposure DESC LIMIT 10;

// Peel chain: >= 5 tx подряд с 2 выходами, «отщеп» < 10 % большего выхода
MATCH p = (s:Transaction {class: 1})-[:FLOWS_TO*5..8]->(:Transaction)
WHERE all(t IN nodes(p) WHERE t.nOut = 2 AND t.outMin < 0.1 * t.outMax)
RETURN length(p) AS hops, [t IN nodes(p) | t.txId] AS chain LIMIT 5;

// Циклы: возврат за 2–4 шага
MATCH p = (w:Wallet {class: 1})-[:SENT_TO*2..4]->(w)
RETURN [x IN nodes(p) | x.address] LIMIT 5;

// Кратчайший путь между двумя кошельками
MATCH (a:Wallet {address: $from}), (b:Wallet {address: $to})
MATCH p = shortestPath((a)-[:SENT_TO*..8]->(b))
RETURN [x IN nodes(p) | x.address], length(p);
```

| Запрос | Результат | Урок |
|---|---|---|
| Fan-in ≥ 100 (4,3 с) | 2 680 кошельков: 2 078 licit, 578 unknown, лишь 24 illicit; топ-1 — 11 213 отправителей, licit | Fan-in — прежде всего сервисы. Моё: 24 / 2 680 ≈ 0,9 % — **ниже** базовых 1,7 % |
| Экспозиция (0,5 с) | Два unknown-кошелька получают средства от 1 061 illicit-кошелька каждый, дальше — 319 и 190 | Одинаковые значения — подсказка, что это адреса одного сервиса: проверить fan-in и офчейн |
| Peel chain (0,14 с) | Условию «2 выхода, малый < 10 %» отвечают 102 777 tx — половина датасета; цепочки ≥ 5 стартуют с 366 illicit-tx, самая длинная — 182 шага | Порог слишком общий |
| Циклы (1,8 с) | Пример идёт через хаб с 11 213 отправителями (licit) | Round-trip через сервис, не обязательно «отмывание» |
| Кратчайший путь | От illicit-кошелька до главного получателя illicit-средств — 2 шага через другой illicit-кошелёк | — |

Замечание (моё) к peel chain: «2 выхода, малый < 10 %» — это форма обычного платежа со сдачей, поэтому условию и отвечает половина датасета. Кроме того, запрос проверяет форму **каждой** транзакции, но не то, что цепочка продолжается именно через **больший** выход. Строже — проверять по двудольному графу (addr → tx → addr), что следующая tx тратит крупный выход.

### Graph Data Science: цикл работы

Проекция → оценка памяти → алгоритм → анализ в Cypher → экспорт в Gephi.

```cypher
// 1. Граф в памяти: кошельки, неориентированно, вес n
CALL gds.graph.project('wallets', 'Wallet',
  {SENT_TO: {orientation: 'UNDIRECTED', properties: 'n'}});
// 2. Сколько памяти нужно?
CALL gds.louvain.write.estimate('wallets', {writeProperty: 'louvain'})
YIELD requiredMemory;
// 3. Алгоритм -> свойство в базе
CALL gds.louvain.write('wallets', {writeProperty: 'louvain',
  relationshipWeightProperty: 'n'}) YIELD communityCount, modularity;
```

Режимы: `stream` — посмотреть результат; `stats` — только итог; `mutate` — в проекцию, для следующего алгоритма; `write` — записать в узлы базы. Проекция живёт в памяти: после работы — `CALL gds.graph.drop('wallets')`.

| Алгоритм | Вопрос расследователя | Нюанс |
|---|---|---|
| WCC | Какие «острова» не связаны между собой? | Базовая кластеризация; гигантская компонента — норма |
| Louvain | Кто взаимодействует плотнее, чем случайно? | Модулярность; `resolution` меняет размер сообществ |
| Leiden | То же, но стабильнее | Гарантирует связные сообщества; запускать на неориентированной проекции |
| Label Propagation | Быстрые сообщества на очень больших графах | Недетерминирован: на слайде — «фиксируйте seed», повторяйте запуск и сравнивайте |
| PageRank | Куда «стекаются» средства? | Высокий у сервисов, коллекторов, бирж |
| Betweenness | Кто посредник между группами? | Дорогой: семплирование или подграф |
| Degree | Fan-in и fan-out | `orientation: 'REVERSE'` — входящая степень |
| FastRP + k-means | Кто похож по форме окружения? | Находит похожих без общих рёбер |

Теория центральностей и сообществ — в [[Лекция 08 — Теория графов в OSINT]].

## Часть 3. Кластеризация

### Три значения слова «кластер»

| | Кластеры адресов | Сообщества в графе | Кластеры признаков |
|---|---|---|---|
| Задача | Entity resolution | Community detection | Feature clustering |
| Вопрос | Какие адреса принадлежат одному владельцу? | Кто взаимодействует плотнее, чем с остальными? | Кто ведёт себя похоже? |
| Метод | Эвристики общих входов и сдачи | WCC, Louvain, Leiden | k-means на признаках или эмбеддингах (FastRP) |
| Результат | Узел = сущность (как в BitcoinTemporalGraph) | Группы кошельков или сущностей | Поведенческие профили |

**В отчёте пишем, какая именно кластеризация применена** — это три разных утверждения. Первая — частный случай [[Лекция 07 — Entity resolution и графы связей|entity resolution]].

### Эвристики кластеризации адресов

- **Общие входы (common-input ownership):** все входы одной tx подписывает один владелец → адреса объединяются.
- **Адрес сдачи (change):** новый выход того же типа, «некруглая» сумма, адрес появляется впервые.
- В статье — эвристики из предыдущей работы авторов (arXiv 2403.00523): 874 млн скриптов → ~252 млн кластеров (в ~3,5 раза меньше).

**Ложное слияние необратимо:** один CoinJoin, пропущенный фильтром, «склеивает» посторонних людей в одну сущность. Замечание (моё): то же делает PayJoin (P2EP) — у него нет равных выходов, поэтому фильтр CoinJoin его не ловит; а кастодиальный сервис даёт «сущность» = биржа со средствами тысяч клиентов, а не человек.

### CoinJoin: почему исключают

Несколько пользователей в одной транзакции; равные выходы прячут, кто кому заплатил; эвристика общих входов даёт ложное слияние. Авторы детектируют CoinJoin эвристиками для JoinMarket, Wasabi, Whirlpool (arXiv 2311.12491) и исключают его **и из кластеризации, и из рёбер** графа. **CoinJoin — сигнал желания приватности, а не доказательство преступления.**

### Сообщества: Louvain и Leiden

- **Модулярность Q** — доля рёбер внутри сообществ минус ожидаемая при случайных связях.
- **Louvain** (Blondel et al., 2008) — жадно переносит узлы между сообществами и «сворачивает» граф уровнями.
- **Leiden** (Traag et al., 2019) — добавляет шаг уточнения: сообщества гарантированно связные.
- **Resolution γ:** больше γ → больше мелких сообществ.

```cypher
CALL gds.leiden.write('wallets', {writeProperty: 'leiden',
  relationshipWeightProperty: 'n', gamma: 1.0})
YIELD communityCount, modularity;
```

Биржи и крупные сервисы — **супервузлы**: они склеивают сообщества. Помечаем или исключаем их до запуска.

### От сообщества к лиду

1. **Сообщество** — доля illicit в разы выше базовой: порог ≥ 10 %. На Elliptic++ максимум — 28 %, а не 50 %.
2. **Кандидаты** — неизвестные кошельки внутри, ранжированные по PageRank. На Elliptic++: 10 сообществ ≥ 10 % → 31 811 кандидатов; топ-1 `1781T…mqt` — он же лидер экспозиции.
3. **Паттерны** — fan-in, peel chain, экспозиция вокруг кандидата: есть ли структурное подтверждение?
4. **Офчейн** — поиск адреса на форумах (BitcoinTalk), метки обозревателей, санкционные списки OFAC, отчёты.
5. **Вывод** — уровень уверенности, альтернативные объяснения, ограничения данных.

Порог считаем от базовой доли, а не «на глаз». **Лид — адрес для проверки, а не подозреваемый.**

### Предсказывает ли граф тип сущности (бенчмарк статьи)

Задача: по признакам узла и его 2-шагового окружения предсказать один из 7 типов. Окружение — 10 соседей на 1-м шаге, 5 на 2-м, 12 выборок на узел; GNN из PyTorch Geometric (2 слоя, 256 нейронов) и GBC из sklearn; разбиение 40/30/30, классы выровнены до 300–1500 образцов.

| Модель | Macro-F1 | Exchange | Mining | Gambling | Ponzi | Individual | Ransomware | Bet |
|---|---|---|---|---|---|---|---|---|
| GCN | 0,56 | 0,43 | 0,45 | 0,56 | 0,46 | 0,88 | 0,19 | 0,98 |
| GraphSAGE | 0,62 | 0,51 | 0,57 | 0,58 | 0,55 | 0,93 | 0,25 | 0,98 |
| **GAT** | **0,64** | 0,49 | 0,57 | 0,62 | 0,57 | 0,93 | 0,32 | 0,98 |
| GIN | 0,63 | 0,54 | 0,54 | 0,62 | 0,60 | 0,94 | 0,21 | 0,98 |
| GBC (без графа) | 0,57 | 0,54 | 0,45 | 0,57 | 0,30 | 0,94 | **0,50** | 0,89 |

Лучшая модель — GAT: окружение помогает. Но ransomware лучше находит GBC без графа.

Где ошибается модель (матрица ошибок; судя по F1 = 0,32 — GAT):
- всё «стекает» в Individual — туда уходят 14–23 % узлов каждого класса, кроме Bet;
- Ransomware: recall 60 %, но F1 0,32 → точность ≈ 0,22 (проверил: P = F1·R / (2R − F1) = 0,192 / 0,88), то есть ~4 из 5 прогнозов «ransomware» ложные;
- Bet — 99 %: отдельный адрес на каждую ставку, структура узнаваема.

Для OSINT: **ML-оценка — очередь проверки, а не атрибуция.** Считаем точность, а не только «сколько нашли».

## Часть 4. Тренды

### Время в данных

| Elliptic++ | BitcoinTemporalGraph |
|---|---|
| 49 шагов, ~2 недели между ними | Метка времени — индекс блока (~10 мин) |
| Шаг — транзакции, подтверждённые в пределах < 3 часов | Ребро: `reveal` (первая tx) и `last_seen` (последняя) |
| Рёбер между шагами нет | Узел: первая и последняя входящая и исходящая tx |
| Кошелёк: `firstStep`, `lastStep` | Возраст = max(last) − min(first); активность делят на возраст; суммы → USD по медианному курсу за период активности |

Сравниваем **скорости, а не абсолютные суммы**: 1 BTC в 2011 и в 2021 — разные «деньги».

### Тренд: illicit по шагам времени

- 104 illicit-tx на шаг в шагах 1–42 → 24 в шагах 43–49.
- Доля illicit среди размеченных: **11,0 % → 2,5 %**.

```cypher
MATCH (t:Transaction)
RETURN t.timeStep AS step, count(*) AS total,
       count(CASE WHEN t.class = 1 THEN 1 END) AS illicit
ORDER BY step;
```

### Дрейф: почему модели «слепнут»

Weber et al., 2019 (исходный Elliptic): обучение на шагах 1–34, тест на 35–49 (70 : 30 по времени). На шаге 43 — внезапное закрытие даркнет-рынка; после него **ни один метод не находит новые illicit-транзакции**, даже Random Forest, переобучаемый после каждого шага.

Что это значит для OSINT:
- экосистема меняется скачками: закрытия рынков, санкции, новые сервисы (пример с воркшопа — Garantex → A7A5 → Grinex);
- старые паттерны устаревают — качество проверяем **по шагам времени, а не в среднем**;
- следим за долей unknown и обновляем метки;
- **тренд без контекста событий — лишь кривая**: накладываем на шкалу реальные события (закрытия, аресты, санкции).

Альтернативное объяснение падения (моё; оно же нужно в ДЗ-13): метки illicit ставились по сервисам, известным на момент разметки, — площадки, возникшие после закрытия рынка, могли просто остаться в unknown.

### Пайплайн Neo4j → Gephi

Подграф (Cypher) → экспорт (APOC) → импорт в Gephi → Statistics → Layout + Appearance → Preview → SVG/PDF.

```cypher
// A. Эго-сеть illicit-кошелька -> GraphML
CALL apoc.export.graphml.query(
  'MATCH p = (:Wallet {address: "1Abc..."})-[:SENT_TO*1..2]-(:Wallet)
   RETURN p LIMIT 2000', 'ego_illicit.graphml', {useTypes: true});
// B. Сообщество -> CSV для Import Spreadsheet
CALL apoc.export.csv.query(
  'MATCH (w:Wallet) WHERE w.louvain = 123
   RETURN w.address AS Id, w.class AS class, w.pagerank AS pagerank',
  'nodes.csv', {});
CALL apoc.export.csv.query(
  'MATCH (a:Wallet)-[r:SENT_TO]->(b:Wallet)
   WHERE a.louvain = 123 AND b.louvain = 123
   RETURN a.address AS Source, b.address AS Target, r.n AS Weight',
  'edges.csv', {});
```

Нужен `apoc.export.file.enabled=true`; файлы появляются в папке `import/`. GraphML сохраняет типы свойств; в CSV колонки `Id` и `Source`, `Target`, `Weight` Gephi распознаёт сам. Эго-сеть на 2 шага даже с `LIMIT 2000` — это 1 319 узлов (у центра 644 соседа).

### Импорт и статистики

| Шаг | Что делать |
|---|---|
| Импорт | File → Import spreadsheet: сначала `nodes.csv` (Id, class, pagerank), затем `edges.csv` → Append to existing workspace; граф Directed |
| Проверка | Data Laboratory: типы колонок (`class` — как текст, чтобы раскрасить), число узлов и рёбер |
| Степени | Statistics → Average Degree: in-degree / out-degree = fan-in / fan-out |
| Сообщества | Statistics → Modularity: Resolution, Use weights, Randomize → Modularity Class |
| Роли | PageRank; Network Diameter → Betweenness и Closeness (медленно на больших графах) |
| Компоненты | Connected Components → Component ID; фильтр Giant Component |

### ForceAtlas2 и Appearance

ForceAtlas2 (Jacomy et al., 2014): **Scaling** растягивает граф; **Gravity** тянет к центру и держит острова рядом; **LinLog mode** — компактнее кластеры; **Dissuade Hubs** — хабы на периферию; **Prevent Overlap** — включать в конце; **Approximate Repulsion** (Barnes-Hut) — для больших графов.

Appearance: цвет узлов — Partition по `class` или Modularity Class; палитра illicit — красный, licit — синий, unknown — серый; размер — Ranking по PageRank или In-Degree; рёбра — толщина по Weight; подписи — только для топ-N узлов. **Одинаковые параметры layout и палитра для всех рисунков отчёта** — иначе картинки несравнимы.

На примере шага 32 Elliptic++ (4 525 tx, 4 952 ребра; illicit 342, licit 981, unknown 3 202):

| Форма | Значение |
|---|---|
| Плотное ядро | Сообщество |
| Звезда | Хаб: fan-in / fan-out |
| Длинная нить | Цепочка, peel chain |
| Узел между группами | Мост, посредник |
| Остров | Отдельная компонента |

### Фильтры для расследования

| Фильтр | Зачем |

| Topology → Ego Network | Окружение лида на глубину 1–2 |
| Topology → Giant Component | Убрать мелкие острова |

Фильтры комбинируются (перетащить один в другой). **Фильтр — часть методологии: записываем, что отброшено.**

## Главное для практики

1. Паттерн, кластер и тренд — это **запросы и метрики с параметрами**, которые можно повторить, а не впечатление от картинки.
2. Большое хранилище — в SQL, подграф расследования — в Neo4j; Gephi — для исследования и рисунка в отчёт.
3. У каждого паттерна (fan-in, fan-out, peel chain, цикл, CoinJoin, мост) есть легитимное объяснение — исключаем его до вывода. На Elliptic++ высокий fan-in даже реже illicit, чем в среднем.
4. Пороги — от данных: перцентили, базовая доля, lift; «на глаз» не годится (peel chain с порогом 10 % поймал половину датасета).
5. «Кластер» — три разных утверждения: адреса одного владельца, сообщество, похожее поведение. Пишем, какое именно.
6. Ложное слияние адресов необратимо; CoinJoin, PayJoin, биржи и супервузлы — главные источники ошибок.
7. Время — отдельное измерение: нормируем по возрасту и курсу, качество проверяем по шагам, тренд накладываем на реальные события; дрейф после закрытий рынков ломает модели.
8. ML-прогноз типа сущности — очередь проверки (точность ransomware ≈ 0,22), а не атрибуция.
9. Научная статья — тоже источник: пересчитываем цифры, прежде чем цитировать.
10. Лид — адрес для офчейн-проверки, а не подозреваемый; близость ≠ причастность.

### Пять типов паттернов

| Тип | Пример сигнала | Чем искать |
|---|---|---|
| **Временной** | Посты каждый вторник в 9:00 → часовой пояс, режим | pandas, матрица активности |
| **Языковой** | Переход с украинского на русский → сменилась аудитория | NLP, тематическое моделирование |
| **Сетевой** | Одни и те же аккаунты всегда репостят вместе → бот-ферма | Gephi, betweenness (см. [[Лекция 08 — Теория графов в OSINT]]) |
| **Контентный** | Тематические кластеры публикаций | TF-IDF, BERTopic |
| **Поведенческий** | Резкая смена частоты постов → что-то произошло | Детекция аномалий (anomaly detection) |

### Временные паттерны: матрица активности

Таблица «день недели × час суток», в ячейке — число публикаций, поверх — тепловая карта (heatmap). Нужны только метки времени, без текста постов.

Что видно:
- пик активности → вероятный часовой пояс;
- рабочее время против личного;
- аномалии — ночь, выходные, всплески.

Минимальная идея в коде (свой набросок, не со слайда):

```python
df["ts"] = pd.to_datetime(df["ts"], utc=True).dt.tz_convert("Europe/Kyiv")
m = pd.crosstab(df["ts"].dt.day_name(), df["ts"].dt.hour)   # день × час
sns.heatmap(m, cmap="YlOrRd")
```

Оговорки (мои): отложенный постинг и боты дают «ровное» расписание; переход на летнее время сдвигает пик на час; пик в 7–9 утра совместим с несколькими поясами — это гипотеза, а не вывод. Всегда храните время в UTC и подписывайте, в какой пояс перевели ось.

По заметкам докладчика: 200+ постов публичного Telegram-канала, только метаданные — 15–20 минут в Jupyter, и пояс автора часто виден сразу. На сайте есть стартовый скрипт `build_activity_matrix(csv, tz_offset)` (seaborn-heatmap, сохранение PNG, печать пикового дня и часа).

### Кластеризация текста

Задача — найти тематические группы **без заранее заданных меток** (обучение без учителя).

| Алгоритм | Суть | Ограничение |
|---|---|---|
| **K-Means** | Делит на заданное число k кластеров | Нужно знать k; плохо на кластерах разного размера и формы |
| **DBSCAN** | Сам находит число кластеров, выделяет шум | Чувствителен к параметрам плотности |
| **BERTopic** | Трансформерный подход, на слайдах — «стандарт 2025–2026» | Медленный на очень больших корпусах (>1 млн документов) |

#### Как устроен BERTopic

1. Эмбеддинги документов (BERT-подобная модель; для смешанного корпуса — `language="multilingual"`).
2. Снижение размерности — UMAP.
3. Кластеризация плотности — HDBSCAN (число тем не задаётся заранее).
4. Описание тем ключевыми словами — c-TF-IDF.

Поправка к слайду: там шаг 4 назван «удаление стоп-слов». На деле c-TF-IDF (class-based TF-IDF) строит **представление темы** — ключевые слова, отличающие кластер от остальных; стоп-слова убирают отдельно (векторизатор).

Применение в OSINT: 1000+ постов Telegram → тематические кластеры; новостной поток → доминирующие нарративы; комментарии → настроения сообщества. Аналитику без ML-бэкграунда, по словам докладчика, достаточно уметь запустить модель и **интерпретировать** результат.

### Тренды: сравнение периодов через TF-IDF

Идея: построить TF-IDF-веса для двух временных окон (например, январь и апрель) и посмотреть, какие слова и биграммы выросли в весе — это кандидаты в новый нарратив.

Подводный камень (мой разбор кода со слайда): если обучить векторизатор только на январе (`fit`) и затем применить к апрелю (`transform`), словарь заморожен январём — **совсем новые апрельские термины не попадут в выдачу**. Правильнее обучать словарь на объединении периодов и сравнивать средние веса, либо считать частоты по неделям как временной ряд.

### Аномалии: Isolation Forest

Признаки по дням: число постов, число уникальных авторов, средний engagement. Модель помечает «выбивающиеся» дни (`-1`) — кандидаты на координированную кампанию, атаку или резкий рост внимания к объекту.

Важно: параметр `contamination=0.05` означает, что модель **в любом случае** объявит аномальными около 5 % дней — даже если ничего не происходило. Найденный день — повод открыть посты за этот день, а не готовый вывод. Связка с алертами — в [[Лекция 14 — Мониторинг в реальном времени и алерты]].

### Кейс: разбор дезинформационной кампании

1. Собрать 5000+ постов по теме (Telegram + X) — методы в [[Лекция 05 — Скрапинг и краулинг соцсетей]].
2. BERTopic → около 8 кластеров нарративов.
3. Временной анализ → когда появился каждый нарратив.
4. Сетевой анализ → кто первым распространял каждый нарратив (см. [[Провенанс и первая публикация]]).
5. Детекция аномалий → дни координированных публикаций.

Результат — **карта нарративов + временная шкала + сеть распространения**. Докладчик советует проговаривать шаги вслух, показывая, что добавляет каждый инструмент.

### Ограничения алгоритмов

- K-Means — требует k, плохо работает на неравных кластерах.
- BERTopic — медленный на корпусах свыше миллиона документов.
- Isolation Forest — сильно зависит от `contamination`.
- Любой алгоритм находит **корреляции, а не причинно-следственные связи**.

### Главное (прежняя версия)

1. Факт — точка, паттерн — смысл; но паттерн — это **гипотеза**, которую проверяют по исходным постам.
2. Матрица активности строится по одним меткам времени: храним UTC, явно указываем пояс оси, помним про отложенный постинг и летнее время.
3. BERTopic — быстрый способ увидеть темы корпуса; названия кластерам даёт аналитик, а не модель.
4. Тренд — сравнение периодов на **общем словаре**, иначе новые термины теряются.
5. Isolation Forest всегда найдёт заданную долю «аномалий» — проверяем каждую вручную.
6. Кейс кампании = нарративы × время × сеть × аномальные дни; первоисточник нарратива ищем отдельно.
7. Алгоритм показывает, куда смотреть; интерпретация, причинность и ответственность — за человеком.
