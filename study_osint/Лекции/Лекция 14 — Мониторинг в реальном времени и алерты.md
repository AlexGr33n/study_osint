## О чём лекция

Инструмент **Groupint** (OSINT for Ukraine), режим **Incidents**: watchlist Telegram-**каналов** (не только групп) → LLM-пайплайн → структурированные карточки событий с координатами на карте Folium → экспорт GeoJSON / JSON / CSV, опционально в Atlos. Формат — лекция + демо пайплайна. Документация — в репозитории `github.com/OSINT-for-Ukraine/groupint`, файл `docs/incidents/overview.md`.

После лекции: собрать watchlist и импортировать списки каналов; пройти пайплайн от `Message` до `Incident`; настроить ключевые слова (глобальные и по каналу); включить планировщик или делать ручной fetch; читать карту и **вручную проверять геолокацию**; выгрузить данные для дальнейшего анализа.

## Событие вместо архива постов

- **Событие (инцидент)** — сообщение о ситуации с последствиями: обстрел, эвакуация, повреждение инфраструктуры.
- Цель — не архив всех постов, а **карточка события**: что, где, когда, из какого канала.
- Выход для аналитика: слой на карте + связь с первичным сообщением в Neo4j. Прослеживаемость: `Message → Incident → канал (Group)`.
- Что даёт: хронологию событий на территории (фильтр по дате), пространственные кластеры — где всплеск сообщений превращается в точки, основу для отчётов, брифингов, экспорта в GIS или Atlos.
- Чего не даёт: **не заменяет спутник и свидетельства** — это быстрый слой гипотез.

## Почему Telegram-каналы

- Оперативные текстовые обновления из регионов в реальном времени.
- Доступ через пользовательский API (Telethon), если ваш аккаунт видит канал; публичные `@channel` и приватные подключаются с разной сложностью.
- Три вызова: **шум** (реклама, репосты, комментарии), **неоднозначные названия** населённых пунктов, **дублирование** одной новости в нескольких каналах.

**Рамки хранилища:** только публичные каналы или те, куда у вас есть законный доступ; проникновение в закрытые чаты — вне рамок.

## Groupint: два режима

| Режим | Назначение | На занятии |
|---|---|---|
| Главная страница | Участники групп, `MEMBER_OF`, endorsements, Gephi | Обзор |
| **Incidents** | Watchlist, LLM-пайплайн, карта событий | Фокус |

Оба режима пишут в один Neo4j, но решают разные задачи. **Incidents не требует скрапинга участников групп** — только посты каналов. Рамки хранилища: сбор списков участников групп — это персональные данные частных лиц, **вне рамок**; используем только режим Incidents. (Графовый режим описан в статье сайта «Telegram network pipeline», см. [[osinter.dev — сайт курса]].)

## Архитектура

Три Docker-контейнера в одной сети `groupint-net`:

| Контейнер | Роль | Адрес |
|---|---|---|
| `groupint-streamlit` | UI Incidents: конфигурация, OTP Telegram, карта, экспорт | http://localhost:18501 |
| `groupint-neo4j` | Хранилище и общая «очередь состояний» сообщений | Bolt :17687, Browser :17474 |
| `groupint-incident-worker` | Планировщик + fetch + пайплайн в фоне; батчи LLM без открытого браузера | — |

UI и worker не дублируют логику в памяти — состояние каждого сообщения живёт в Neo4j. Порядок этапов зафиксирован в `core/incidents/pipeline.py`. **Планировщик в UI не заменяет worker** — нужен запущенный контейнер. Ручные кнопки: *Fetch watchlist now*, *Run pipeline now*.

## Предусловия и запуск

| Компонент | Зачем |
|---|---|
| Docker | Neo4j + Streamlit + worker одной командой |
| `api_id` + `api_hash` | Telethon, получить на my.telegram.org |
| Ключ LLM API | filter + extract (Anthropic или OpenAI) |
| `GOOGLE_MAPS_API_KEY` | Опционально; иначе Nominatim |

Без LLM fetch работает, но **инциденты на карте не появятся**.

```bash
cp .env.example .env        # TELEGRAM_*, ANTHROPIC_API_KEY или OPENAI_API_KEY
./scripts/up-desktop.sh
docker logs -f groupint-incident-worker
curl -sf http://localhost:18501/_stcore/health
```

Neo4j Browser — http://localhost:17474 (`NEO4J_AUTH=none`). Замечание (моё): база без пароля допустима, только если порты опубликованы на `127.0.0.1`; если compose публикует их на всех интерфейсах, собранные данные открыты всей сети — проверить секцию `ports`.

## Авторизация Telegram

Вход: `api_id`, `api_hash`, телефон (secrets или форма). Шаги на вкладке Incidents: *Create / connect Telegram client* → код OTP в приложении Telegram → *Verify secret code* → StringSession на диск (`GROUPINT_SESSIONS_DIR`); после F5 — автопереподключение. Ошибка `SessionInUseError` — на номер допускается одна активная сессия.

## OPSEC

- Отдельный Telegram-аккаунт для OSINT-задач (по возможности).
- `api_id` / `api_hash` — только в `.env` или `.streamlit/secrets.toml`, не в git.
- StringSession (файл `.string`) — как пароль сессии; не пересылать в чаты.
- Docker volume с сессиями — бэкап только на защищённом носителе.
- Ротация ключей LLM при утечке; не показывать реальные ключи на экране.

Рамки хранилища: «отдельный аккаунт» = ваш собственный второй аккаунт на номер, оформленный на вас; вымышленные персоны и пулы аккаунтов — вне рамок (см. навык `osint-collection`).

## Watchlist каналов

`WatchlistChannel` в Neo4j — перечень источников:
- `channel_ref` — `@name` или `https://t.me/...`;
- `enabled` — входит ли канал в опрос; канал можно временно выключить, не удаляя;
- `last_polled_at` — когда последний раз читали посты;
- связь с `Group` появляется после первого успешного fetch.

**Массовый импорт** (expander *Add multiple channels*): текст по одному каналу на строку или файл `.txt` / `.csv` / `.json` (парсер `watchlist_channels.py`) → *Add all to watchlist* → merge в Neo4j; дубликаты обновляются, а не роняют импорт. Так мониторинг на 20–50 каналов стартует за минуты.

## Ключевые слова

| Уровень | Как работает |
|---|---|
| Глобальные | `IncidentMonitorConfig` — singleton в Neo4j; термины через запятую или с новой строки; **логика OR** — достаточно одного совпадения; *Enable global keywords* включает/выключает без удаления списка; пустой список + выключено → глобальный фильтр не действует |
| По каналу | Свой список в expander канала (лексика источника); *Also use global keywords* — объединение списков; `use_global = false` — только локальные; оба выключены → **все сообщения идут в пайплайн** |

Пример: глобально «обстріл»; для морского канала — «корабель», «порт».

Замечания (мои): ключевые слова отвечают за **полноту** — то, что отсёк префильтр, LLM уже не увидит; проверяйте фильтр на выборке постов. Для украинской морфологии: если сопоставление идёт по подстроке, задавайте основы («удар» ловит «удари», «ударів», «ударом»; «удари» не ловит «ударів»); если по токенам — перечисляйте формы. Как именно — смотреть в `core/incidents/keyword_prefilter.py`.

## Планировщик и опрос

Блок *Message fetch scheduler* (хранится в Neo4j):
- `scheduler_enabled` — worker опрашивает автоматически;
- `fetch_interval_sec` — минимум секунд между циклами (например, 1800);
- `run_pipeline_after_fetch` — LLM сразу после ingest;
- `last_fetch_at` — время последнего опроса; *Save scheduler* — применить для worker.

Рекомендация: **сначала ручной fetch, потом планировщик.**

*Fetch watchlist now* использует Telethon-сессию из браузера, читает новые посты всех `enabled`-каналов, пишет `Message` в Neo4j, обновляет `last_fetch_at`. LLM не запускает, если не нажато *Run pipeline* и не включён `run_pipeline_after_fetch`.

Фоновый worker (`incident-worker.py`): каждый цикл читает планировщик → прошёл ли интервал → `poll_all_watchlist` через Telegram (переменные `TELEGRAM_*`) → опционально `run_pending_pipeline`. Без ключа LLM ingest идёт тихо, без спама ошибок. Важно: worker авторизуется **по `.env`, а не по сессии из UI** — отсюда типовая ошибка «Worker auth error».

## Пайплайн: от Message к Incident

| # | Этап | Вход | Действие | Выход |
|---|---|---|---|---|
| 0 | **ingest** | Новые посты из Telegram API | Запись `Message` + связь с `Group`; существующие `message_id` не перезаписываются (инкрементально) | `text`, `date`, `message_id`, `group_id`, `incident_pipeline_stage` |
| 1 | **keyword_prefilter** | Сырой текст, ещё без `text_clean` | `effective_keywords()` = глобальные + по каналу | Дальше или отсечение без LLM — экономия токенов |
| 2 | **clean** | Прошедшие префильтр | Нормализация; с LLM — промпт `CLEANER_SYSTEM`, без LLM — копия текста | `text_clean`, stage `cleaned` |
| 3 | **filter** (`incident_filter`) | `text_clean` | LLM отвечает JSON: это сообщение о событии, которое можно нанести на карту? Провайдер — `INCIDENT_LLM_PROVIDER` | `incident_checked = 1` или `-1`, stage `filtered`; не инцидент → пайплайн для сообщения останавливается |
| 4 | **dedupe** | Сообщения-инциденты | `run_dedupe_batch` — кластеризация похожих событий; **до** extract | Меньше дублей на карте при репостах |
| 5 | **extract** | `text_clean` после filter + dedupe | LLM `EXTRACT_SYSTEM` → JSON | `category`, `location_text` (напр. «Костянтинівка, Донецька обл.»), stage `extracted` |
| 6 | **geocode** | `location_text` + контекст | Google Maps API или Nominatim | `lat`, `lon`; stage `geocoded` или `geocode_failed` |
| 7 | **link** | `Message` с координатами, категорией, summary | `run_link_incidents_batch` → `merge_incident_from_message` | Узел `Incident` + `(Message)-[:REPORTS]->(Incident)`, `(Incident)-[:FROM_CHANNEL]->(Group)` |

Замечания (мои):
- **Текст поста — недоверенные данные.** Он идёт в промпты clean/filter/extract, и пост с инструкцией для модели может сломать фильтр. Передавать как данные в тегах и валидировать JSON — см. [[Лекция 02 — Промптинг, контроль качества и RAG]] и [[Лекция 10 — Автоматизация сбора и гигиена данных]].
- **Дедупликация ≠ подтверждение.** Один взрыв в пяти каналах — одна точка, но и не пять независимых подтверждений: копии одного источника не корроборация. Полезно хранить, сколько каналов сообщили и кто был первым ([[Провенанс и первая публикация]]).
- **Время:** `Message.date` — время публикации, а не события; откуда берётся `Incident.occurred_at`, надо проверить. Хранить в UTC.
- **Nominatim:** публичный сервер требует не чаще 1 запроса в секунду, осмысленный User-Agent и не допускает массовой нагрузки; для больших объёмов — свой инстанс или кэш.
- Стадия в узле `Message` — это конечный автомат: пайплайн можно прервать и продолжить без повторной обработки ([[Идемпотентность и dedup]], [[Инкрементный сбор по курсору]]).

## Модель данных Neo4j

| Узел | Ключевые поля |
|---|---|
| `Message` | `text_clean`, `lat`, `lon`, `pipeline_stage` |
| `Incident` | `category`, `summary`, `occurred_at`, `atlos_slug` |
| `Group` | `channel_ref`, `title` |

Связи: `(Message)-[:REPORTS]->(Incident)`, `(Incident)-[:FROM_CHANNEL]->(Group)`, `Message` — `Group`.

## Карта, верификация, экспорт, отчёт

**Карта (Folium), вкладка *Incident map*:** маркеры из `Incident.lat` / `lon`; цвет и фильтр по категории; фильтр по диапазону дат; popup — summary, `location_text`, ссылка на источник; обновляется после *Run pipeline* или цикла worker. Это не GIS — обзор и брифинг; для QGIS — экспорт GeoJSON.

**Верификация геолокации — обязательный шаг аналитика:**
1. Сравнить `location_text` с текстом поста.
2. Проверить координаты на OSM или спутнике.
3. Одноимённые сёла — типичная ошибка геокодера.
4. LLM может выдумать район или перепутать область.

**Карта = гипотеза** для дальнейшего подтверждения; уровень уверенности документируется в отчёте команды. Замечание (моё): если в посте указан только город или область, геокодер вернёт центроид — точка выглядит точной, хотя точность «уровень населённого пункта». Стоит записывать точность (адрес / населённый пункт / область).

**Экспорт** (с учётом фильтров карты): GeoJSON — QGIS, ArcGIS; JSON — Python / jq; CSV — Excel, статистика. Назначение — архив эпизода мониторинга и передача другим командам; **экспорт не заменяет Neo4j** для исторического граф-анализа.

**Atlos (опционально)** — совместная платформа инцидентов: API v2 `POST /api/v2/incidents/new`; в UI *Export to Atlos*, *Test connection*; локально `./scripts/up-full.sh`, http://localhost:13000; `atlos_slug` на `Incident` защищает от повторного экспорта.

**Отчёт разведки** — *Generate intelligence report*: текстовая сводка по тем же фильтрам, что и карта (категории, локации, хронология словами) для брифинга руководству или партнёрам. LLM может обобщить с ошибками — **факты проверять по первичным `Message`**.

Замечание (моё) о публикации: свежие точки прилётов и любые данные о позициях не публикуются — это помогает противнику корректировать огонь. Внутренняя карта команды ≠ публикация; наружу — с задержкой и по правилам организации.

## Ручной vs автоматический OSINT

| Ручной | Groupint Incidents |
|---|---|
| Скролл ленты каналов | Планировщик + Neo4j |
| Таблица в Excel | Связь `Incident` + `Message` |
| Точки на карте вручную | Folium + пайплайн геокодирования |

Автоматизация масштабирует охват; **аналитик остаётся на верификации**.

## Типовые ошибки и ограничения

| Симптом | Что проверить |
|---|---|
| Нет точек на карте | Ключ LLM, *Run pipeline*, `geocode_failed` |
| Fetch 0 messages | Канал `enabled`? Аккаунт видит канал? |
| Планировщик не работает | Worker запущен? `scheduler_enabled`? |
| Пустая карта после фильтра | Диапазон дат, категория |
| Worker auth error | `TELEGRAM_*` в `.env` для worker |

Ограничения системы:
- качество событий = качество текста в канале;
- rate limits Telegram — большой watchlist + короткий интервал;
- LLM даёт ложные срабатывания и пропуски;
- стоимость токенов LLM при выключенном keyword-фильтре;
- геокодирование: омонимы, отсутствие адреса в посте;
- **не детектирует манипуляции изображениями** — анализируется только текст поста (проверка медиа — [[Лекция 04 — Верификация и противодействие манипуляциям]]).

## Демо, учебный кейс и практика

**Чеклист демо (15–20 мин):** `up-desktop.sh` → OTP в Incidents → watchlist (+ bulk) → global keywords → per-channel (опционально) → *Save scheduler* или *Fetch now* → *Run pipeline now* → карта и клик по маркеру → верификация 1–2 точек → экспорт JSON / GeoJSON.

**Учебный кейс:** 3 канала, глобальные слова `обстріл`, `удари`, интервал 30 мин. Bulk import watchlist → включить `run_pipeline_after_fetch` → дождаться 2 циклов worker (или 2× *Fetch* + *Run pipeline*) → фильтр карты по категории → проверить 2 маркера на спутниковой карте → в отчёте одна точка подтверждена, одна отклонена, и почему.

**Практика (45–60 мин):** 1 канал, 5 ключевых слов, *Fetch* + *Run pipeline*, JSON с 3 инцидентами, абзац о верификации геолокации.

**Ресурсы:** [github.com/OSINT-for-Ukraine/groupint](https://github.com/OSINT-for-Ukraine/groupint) (Issues — техподдержка); в `docs/`: `index.md` (хаб), `tutorial-full-workflow-uk.md` (полная цепочка на украинском), `incidents/overview.md` (пайплайн), `incidents/keywords-and-scheduler.md`.

## Главное для практики

1. Мониторинг событий = не архив постов, а **карточка события** (что, где, когда, откуда) со связью до первичного сообщения.
2. Порядок пайплайна: ingest → keyword_prefilter → clean → filter → dedupe → extract → geocode → link; стадия хранится в базе, поэтому процесс возобновляем.
3. Ключевые слова экономят токены, но задают полноту: проверяем префильтр на выборке и учитываем морфологию.
4. Сначала ручной fetch, потом планировщик; worker — отдельный контейнер со своими `TELEGRAM_*`.
5. Дубли по репостам схлопываем, но копии одного источника не считаем подтверждением.
6. Каждая точка на карте — гипотеза: сверяем `location_text` с постом, координаты — с OSM/спутником, помним про одноимённые сёла, выдумки LLM и центроиды.
7. OPSEC: ключи и StringSession вне git и чатов, отдельный собственный аккаунт, база без пароля — только на localhost; свежие точки ударов не публикуем.
8. Автоматизация масштабирует охват, верификация остаётся за аналитиком.

Переход от **реактивного** OSINT (ищем, когда уже поздно) к **проактивному** мониторингу (узнаём раньше других). Ставка — на бесплатные и условно бесплатные средства: RSS, Telegram-через-RSS, Google Alerts, публичные API, no-code-связки; вторая половина — как не утонуть в алертах. С PDF-версией версия сайта стыкуется так: Groupint Incidents — это самостоятельно развёрнутый стек уровня 1 «пирамиды» ниже, где keyword-фильтр дополнен LLM-фильтром, а уровни приоритета алертов применимы к категориям инцидентов.

### Зачем мониторинг

Сценарии со слайда:
- новое упоминание клиента или партнёра в прессе → реакция до широкой огласки;
- появление утечки данных (своей организации) → реакция за часы, а не дни;
- сдвиг нарратива вокруг объекта → ранняя эскалация;
- новая активность отслеживаемого объекта → обновление досье.

**Рамки хранилища:** объект мониторинга — тема, организация, бренд, публичная роль или собственная экспозиция; постоянное наблюдение за частным лицом — **вне рамок хранилища**.

### Пирамида инструментов

| Уровень | Стоимость | Примеры |
|---|---|---|
| 4 | Платные enterprise-платформы | Crimewall, Recorded Future, Maltego Pro |
| 3 | ~$10–50/мес | Brand24, Mention, Talkwalker |
| 2 | Условно бесплатные | Google Alerts, IFTTT |
| 1 | Полностью бесплатные | RSS + Telegram + Python |

Цель курса — уровни 1–2: по оценке лектора, это ~80 % возможностей без лицензионных ловушек. Дорогие платформы выигрывают масштабом и доступом к закрытым источникам, но для большинства задач аналитика не нужны.

### RSS — фундамент бесплатного мониторинга

Подписка на обновления по стандартному протоколу. Типовые адреса фидов:

| Источник | Шаблон фида |
|---|---|
| Новостные сайты | почти у всех есть RSS |
| YouTube-канал | `youtube.com/feeds/videos.xml?channel_id=<ID>` |
| Reddit | `reddit.com/r/<сабреддит>.rss` |
| Google News | `news.google.com/rss/search?q=<запрос>` |
| GitHub | фиды релизов, коммитов, issues |

Читалки: Inoreader (на слайде — 250 бесплатных фидов; лимиты бесплатных тарифов меняются, сверять), Feedly. Self-hosted вариант — Miniflux.

### Telegram как канал мониторинга

- Конвертеры канала в RSS: **RSS.app**, **RSSHub** (открытый, можно развернуть у себя; на слайде записан как «RSS.hub»), **FetchRSS**.
- Схема: фид для `@канал` → добавить в Inoreader → настроить фильтр по ключевым словам.
- Альтернатива — веб-превью публичного канала `t.me/s/<канал>` как источник для конвертера.
- **Osavul** — коммерческая платформа мониторинга Telegram (на слайде: 150 000+ каналов).

Докладчик предлагает прямо на лекции превратить публичный канал в RSS — это занимает пару минут. Telegram назван ключевым каналом для постсоветского пространства.

### Google Alerts и Google News

- **Google Alerts**: запрос с вариантами написания через `OR` и кавычками, частота (сразу / раз в день / раз в неделю), источники (новости, блоги, веб), доставка на email **или как RSS-фид** — последнее удобно складывать в ту же читалку.
- **GNews** (Python-библиотека поверх Google News): язык, страна, период, лимит результатов.

### Архитектура keyword-алертинга

```
Источники → Сбор → Фильтрация → Нормализация → Алерт
RSS/API/    cron,   совпадение    дедупликация,  email /
Telegram/   планиров- по ключевым  оценка          Telegram /
веб         щик       словам       достоверности   Slack
```

На слайде — простейший цикл на библиотеке `schedule`: каждые 30 минут прочитать фиды, отфильтровать по ключевым словам, убрать дубли, отправить в Telegram-бот. Чего в этом наброске не хватает для реальной работы — см. заметки-техники: память увиденного между запусками ([[Инкрементный сбор по курсору]], [[Идемпотентность и dedup]]), паузы и повторы ([[Rate limit и backoff]]), контроль того, что фид не «замолчал» без ошибки ([[Тихие поломки сборщика]]).

### No-code: IFTTT, Zapier, Make

- **IFTTT** — простые связки: Google Alert → уведомление в Telegram, RSS → Google Sheets, новое видео → email.
- **Zapier** — сложнее сценарии, больше интеграций (на слайде: бесплатно до 100 задач в месяц).
- **Make** (бывший Integromat) — самый мощный no-code вариант (на слайде: до 1000 операций в месяц бесплатно).

Self-hosted альтернатива всем трём — n8n из [[Лекция 10 — Автоматизация сбора и гигиена данных]]; встраивание в рабочий процесс — [[Лекция 16 — Интеграция AI в рабочие процессы OSINT]].

### Управление алертами: против перегрузки

Аналитик, получающий 500 алертов в день, не читает ни одного. Решение — уровни приоритета:

| Уровень | Канал и частота | Что сюда попадает |
|---|---|---|
| 🔴 Критический | Сразу (Telegram/SMS) | Новая статья в СМИ, утечка, упоминание в криминальном контексте |
| 🟡 Важный | Ежедневный дайджест (email) | Новые посты в соцсетях, смена роли, новая компания |
| 🟢 Фоновый | Еженедельный обзор (RSS/Obsidian) | Общие тематические новости, слабо связанные упоминания |

Сигналы-всплески (резкий рост упоминаний за час или день) удобно ловить методами детекции аномалий из [[Лекция 13 — Паттерны, тренды и кластеризация]].

### «Тёмная сеть» — базовый уровень

На слайде перечислены сервисы проверки утечек: HaveIBeenPwned, BreachDirectory, DeHashed, Leak-Lookup — и пример запроса к API HIBP.

- В рамках хранилища допустимо одно: проверить **собственный** email (или email организации по её поручению) через HIBP, чтобы оценить свою экспозицию — см. [[Удаление своих данных]].
- Поиск по агрегаторам утечек (BreachDirectory, DeHashed, Leak-Lookup) и любые запросы о чужих людях — **вне рамок хранилища**, см. [[Пробив и дата-брокеры]].
- Фактическая поправка: на слайде API HIBP назван бесплатным. Поиск по email через API v3 требует платного ключа (с 2019 г.); бесплатны веб-проверка на сайте и сервис Pwned Passwords.

### Архитектура дашборда мониторинга

| Слой | Содержимое |
|---|---|
| Сбор | RSS → Inoreader или self-hosted Miniflux; Telegram → RSS.app → та же читалка; Google Alerts → email или RSS |
| Фильтрация | Python-скрипт: ключевые слова + тональность; дедупликация по URL и содержимому |
| Вывод | 🔴 → алерт Telegram-бота · 🟡 → ежедневный email-дайджест · 🟢 → еженедельный отчёт в Obsidian |

### Главное (версия сайта)

1. Мониторинг — это проактивность: настроенная система сообщает о событии раньше, чем вы начнёте искать.
2. Уровни 1–2 пирамиды (RSS, Telegram→RSS, Google Alerts, Python) закрывают большинство задач без лицензий.
3. Google Alerts и Telegram отдаём в RSS — всё сходится в одну читалку или один скрипт.
4. Пайплайн алертов = сбор → фильтр → нормализация и дедупликация → доставка; память увиденного и контроль «тихих» фидов обязательны.
5. Три уровня приоритета и разные каналы доставки — иначе алерты превращаются в шум.
6. Записываем, что **не** отслеживается — пробелы покрытия часть отчёта.
7. Утечки — только собственная экспозиция через HIBP; агрегаторы утечек и чужие email — вне рамок.
