# ДЗ №5 — Інкрементний колектор Mastodon

Курс «AI для OSINT 2026», лекція «Соцмережі та медіапростір: збір, моніторинг, базовий аналіз».

Колектор збирає публічні пости з **хештег-стрічок Mastodon** (офіційний REST API, без логіна)
інкрементно за id-курсором, поважає ліміти інстансу і складає все в одну канонічну таблицю SQLite
`author · url · date · text (+ media)`. Звіт про ліміти — [REPORT.md](REPORT.md).

## Що де

## Запуск

```bash
python -m venv .venv && .venv\Scripts\activate      # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env                                 # за потреби змініть паузи, UA, токени, проксі
python -m collector run                              # інкрементний прогін: лише нове після курсора
python -m collector backfill --pages 2               # одноразовий добір старішої історії, порціями
python -m collector stats                            # зведення: записи, курсори, коди відповідей
python -m collector export                           # → data/sample.jsonl (або --format csv --out data/sample.csv)
python -m collector dashboard                        # → data/dashboard.html
python -m pytest -q                                  # тести
```

Docker (бонус): `docker compose up -d` — прогін кожні 30 хв, база й логи в `./data` і `./logs`.
Разові команди в контейнері: `docker compose run --rm cli backfill` (так само `stats`, `export`, `dashboard`).

Відносні шляхи з `.env` (`COLLECTOR_DB`, `TARGETS_FILE`) і `logs/` рахуються від кореня проєкту, а не від поточної теки.
Тому запуск із планувальника чи з іншої теки працює з тією самою базою й курсорами.
Одна ціль: `python -m collector run --target "mastodon.social#osint"`. Якщо такої цілі немає в конфігу, команда завершиться з кодом 2.

## Як виконано вимоги

**Інкрементність.** Для кожної цілі (`instance#tag`) у таблиці `cursors` лежать `min_id` (найновіший
зібраний id) і `max_id` (найстаріший). `run` просить `min_id=<курсор>` — Mastodon віддає пости одразу
після нього, тож навіть після довгої перерви дірок немає: наступний прогін продовжує з того ж місця.
Перший прогін бере лише свіжу сторінку; стару історію добирає `backfill` через `max_id` до порожньої
відповіді (`backfill_done=1`). Один прогін = не більше `MAX_PAGES_PER_RUN` сторінок × 40 постів. Колектор гортає до
порожньої сторінки, бо деякі сервери ріжуть `limit` нижче 40. Якщо бюджет сторінок вичерпано, а нове ще є,
у лог іде алерт «ціль відстає».

**Курсор не випереджає дані.** Вставка пачки і зсув курсора — одна транзакція SQLite
(`Store.save_page`). Падіння посеред прогону лишає курсор на останній записаній сторінці.

**Dedup / ідемпотентність.** `uid = sha256("mastodon|" + uri)`, де `uri` — канонічний ActivityPub-id
поста. Він однаковий для копії поста на будь-якому інстансі, тож той самий пост з `#ukraine` і `#україна`
або з `mastodon.social` і `mastodon.online` записується один раз. Додатково `UNIQUE(instance, source_id)`.
Запис — `INSERT OR IGNORE`; повторний прогін без курсора дає лише дублі (перевірено тестом).

**Ліміти.** Між запитами до одного хоста — `REQUEST_DELAY` (1,5 с ⇒ ≤ 200 запитів за 5 хв при ліміті 300).
Кожна відповідь пишеться в `requests` з `X-RateLimit-Limit/Remaining/Reset` і `Retry-After`.
Коли `remaining ≤ 10`, клієнт сам чекає до `X-RateLimit-Reset`, не доводячи до 429.
На 429 — пауза за `Retry-After` (секунди або HTTP-дата), інакше за `X-RateLimit-Reset`, інакше
експоненційний backoff з jitter. Якщо сервер просить чекати довше `MAX_WAIT`, ціль мʼяко відкладається.

**Класифікація помилок** (як у кейсі з лекції):

| Відповідь | Дія |
|---|---|
| 200 з JSON | записати, зсунути курсор |
| 200 без JSON, 5xx, 409, мережа | повтор з backoff; після `MAX_RETRIES` — `deferred`, курсор не рухається |
| 429 | пауза за заголовками; з токенами — кулдаун лише цього ключа, запит одразу йде з вільним |
| 401 з токеном | токен виключено з ротації |
| 3xx, 403, 404, інші 4xx | `skipped`, без марних повторів; на редиректи не переходимо |
| невалідна ціль у конфігу (не ASCII-домен, IP, тег не `\w+`, бракує полів) | `skipped` ще до запиту |
| пост з битою датою або без обовʼязкових полів | пропускається як `malformed`, решта сторінки зберігається |

Збій однієї цілі не валить прогін: вона отримує статус у `cursors`, рядок у `runs`, решта цілей збирається.
Навіть якщо не вдалося записати сам статус (база заблокована), прогін іде далі.
Алерт у лог, якщо за прогін отримано 0 постів або в записах бракує обовʼязкових полів (тиха поломка API).

**Канонічна модель** (`posts`, експорт без `raw`):

| Поле | Зміст |
|---|---|
| `uid` | sha256(platform\|uri), ключ dedup |
| `platform`, `instance`, `source_id` | звідки й під яким id (курсор) |
| `author`, `author_url` | `user@domain` і профіль |
| `url` | посилання на пост |
| `date` | час публікації, ISO-8601 UTC |
| `text` | текст без HTML (абзаци й `<br>` → переноси) |
| `lang`, `media` | мова; вкладення `[{type, url, description}]` — лише посилання, файли не завантажуються |
| `query`, `collected_at`, `collector` | атрибуція: з якої цілі, коли, якою версією зібрано |
| `raw` | сирий JSON відповіді (лише в базі, для аудиту) |

**Конфіг і секрети.** Усе налаштування — у `.env` (шаблон `.env.example`, сам `.env` у `.gitignore`).

## Бонуси

- **Backfill історії** — `python -m collector backfill`, окремий курсор `max_id`, порціями.
- **Дашборд** — `python -m collector dashboard`: записи за цілями й днями, мови, курсори, коди відповідей
  з мінімальним `remaining`, останні прогони.
- **Ротація ключів** — `MASTODON_TOKENS=host=tok1,host=tok2`: найменш нещодавно використаний ключ першим,
  429 охолоджує лише свій ключ, 401 виключає ключ. Лише для **власних** токенів застосунку: ліміт Mastodon
  рахується на акаунт, тож кілька токенів одного акаунта його не множать, а чужі чи фейкові акаунти поза рамками.
- **Проксі-вихід** — `COLLECTOR_PROXY=http://…` або `socks5://…` (SOCKS-підтримка вже в `requirements.txt`).
  Проксі ховає лише IP; перед прогоном варто перевірити фактичний вихідний IP.
- **Docker / docker-compose** — `Dockerfile`, `docker-compose.yml` (сервіс за розкладом + `cli` для разових команд), `.dockerignore`.

## Рамки й етика (до першого запиту)

1. **Чи потрібні дані?** Для учбового моніторингу медіапростору за темою «Україна / OSINT» потрібні лише
   автор, посилання, дата, текст, мова й посилання на медіа. Підписники, біо, аватари в канонічну модель не йдуть.
2. **Законна підстава і ToS.** Лише публічні пости (`visibility=public`) через офіційний API без авторизації.
   Пости авторів, які вимкнули індексацію (`indexable=false` або `noindex=true`), **не збираються** —
   у Fediverse це явна відмова від пошуку. Чесний User-Agent з контактом, пауза між запитами.
3. **Хто бачить цілі?** Лише адміністратори двох інстансів; сторонніх скрапінг-платформ немає.
4. **Валідація вводу.** Хост і тег перевіряються регулярками до запиту.
5. **Зберігання.** База `data/collector.db` локальна й не комітиться; у репозиторії — експорт без `raw`.
   Для учбової мети дані варто видалити після оцінювання.

`targets.demo.toml` — ті самі цілі плюс дві навмисно зламані (неіснуючий інстанс і тег `bad tag/../x`),
щоб показати стійкість прогону; їхні статуси видно в `stats` і на дашборді.
