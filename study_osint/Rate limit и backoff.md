# Rate limit и backoff

Цель — ни одного бана и ни одного лишнего 429. Главный урок лекции: **причину лимита измеряй по логам,
а не угадывай**. В кейсе Telegram банили за объём resolve, а не за частоту запросов.

## Как
1. **Журналируй каждый ответ:** код, `X-RateLimit-Limit/Remaining/Reset`, `Retry-After`, время ответа.
   Это и данные для отчёта, и источник фактического лимита.
2. **Пейсинг по хосту:** пауза между запросами к одному хосту, подобранная так, чтобы не превысить окно.
   Пример: Mastodon даёт 300 запросов за 5 минут, при паузе 1,5 с выходит ≤ 200.
3. **Адаптивное замедление:** когда remaining ≤ N, жди до `Reset` сам, не доводя до 429.
4. **На 429:** жди по `Retry-After` (секунды или HTTP-дата), иначе по `X-RateLimit-Reset`, иначе
   экспоненциальный backoff с jitter (1→2→4→8 с). Время без часовой зоны считай UTC.
5. **Потолок ожидания (`MAX_WAIT`):** если сервер просит дольше, мягко отложи цель (`deferred`).
   Курсор не двигается, следующий прогон продолжит.
6. **Ключи:** 429 охлаждает только свой ключ. Если есть свободный, запрос сразу идёт с ним. Истёкший кулдаун
   должен возвращать ключ в ротацию, иначе после одного 429 ротация сводится к одному ключу.

## Классификация ошибок

| Ответ | Действие |
|---|---|
| 5xx, 409, сеть, 200 без JSON | повтор с backoff, потом `deferred` |
| 429 | пауза по заголовкам, кулдаун только этого ключа |
| 401 | токен исключить из ротации |
| 3xx, 403, 404, прочие 4xx | `skipped` без повторов; по редиректу не переходить, иначе обойдёшь валидацию хоста |

Дорогие операции (resolve, lookup) кэшируй, а бюджет на них считай **до** попытки.
